================================================================================
0. PRODUCT DEFINITION
================================================================================

0.1 WHAT IS BEING BUILT
BhuNex GIS Converter is a single Chrome MV3 extension that converts spatial
and survey data between formats entirely on the user's own machine.

Product identity, in priority order:
  1. Land survey / geomatics
  2. GIS
  3. CAD (survey-grade CAD, not architectural BIM)
  4. Mine survey / geology
  5. LiDAR / point cloud
  6. Raster / DEM
It is NOT a generic office file converter and MUST NOT look like one.

0.2 ONE-SENTENCE CONTRACT
"Drop any survey, GIS, CAD, LiDAR, raster or mining file; the extension tells
you exactly what it is, exactly what it can become, converts it locally, and
proves the conversion was faithful."

0.3 THE PIPELINE (invariant for every conversion)
  INGEST -> DETECT -> INSPECT -> CIR -> TARGET SELECT -> CONFIGURE
        -> CONVERT (worker/native) -> RE-IMPORT -> QA -> PACKAGE -> DELIVER

0.4 WHY A CANONICAL INTERMEDIATE REPRESENTATION (CIR)
N formats with point-to-point converters costs N*(N-1) code paths.
With a CIR it costs 2N: one reader and one writer per format.
Every reader produces CIR. Every writer consumes CIR. There are NO direct
format-to-format shortcuts. This rule has no exceptions.

1. NON-NEGOTIABLE RULES (violation = build rejected)
================================================================================

R1   Never claim a format is supported unless a real reader/writer exists AND
     its capability test passes. The registry flag is derived from tests, never
     hand-written optimism.
R2   Never fabricate coordinates, CRS, extents, elevations, feature counts or
     point counts. Unknown is a first-class value and MUST be displayed.
R3   Never silently drop geometry, Z, M, attributes or metadata. Any loss is
     surfaced as a named, counted warning before and after conversion.
R4   Never silently change CRS, axis order or units. A transform is an explicit,
     recorded operation.
R5   Never parse compressed LAZ as uncompressed LAS. Without a real LAZ codec,
     LAZ reports "compressed payload - decoder not installed".
R6   Never rename a file extension and call it a conversion.
R7   Never present DWG as browser-native. DWG is an ADAPTER through the native
     messaging host and shows its engine status honestly.
R8   Processing is local by default. No network request carries user file bytes.
     There is no telemetry in any conversion path.
R9   Anything above the worker threshold runs off the UI thread. The UI never
     freezes.
R10  Full numeric precision is preserved internally. Rounding is an output
     setting only, and display rounding never feeds back into computation.
R11  Every conversion returns a QA summary. "Converted" alone is not a result.
R12  Reused Geo-Studio engines MUST be ported into the shared conversion core
     without breaking their original behaviour or their tests.
R13  The ODA/DWG integration from the Universal Converter prototype is reused as
     an ADAPTER, not as the architecture.
R14  Mixed-format batch conversion is mandatory.
R15  No CDN, no remote script, no remote stylesheet, no remote font, no runtime
     download of engines. The packaged extension MUST work with the network
     interface disabled.
R16  Input structure = output structure. Layers, folder nesting and archive
     nesting present in the source MUST be reconstructible in the delivery. A
     layer hierarchy is carried as path segments, never as a flattened name, and
     is rebuilt as real folders (in a ZIP) or real containers (KML folders, DXF
     layers) on the way out. Where a target format cannot express the hierarchy,
     the structure is preserved in the delivery tree instead, and the fact is
     stated - never silently flattened.

The following are carried over from the supplied Master Build Instructions.
Its rules 3, 4, 5, 6, 10, 11, 12, 13, 20 are already stated above as R2, R4,
R3, R3, R1, R8, R8, R9 and R11 respectively and are not restated.

R17  Additive change only. Working functionality MUST NOT be removed to make
     room for new functionality. A replacement is permitted only when the
     implementation being replaced is defective, and the commit MUST say so.
     (Master rules 1 and 2.)
R18  Never silently repair uncertain geometry. Repair is off by default,
     previewed before it is applied, counted when it is, and never applied to
     cadastral, lease or other legally operative boundaries without explicit
     per-operation confirmation. (Master rules 7 and 18.)
R19  Every edit is reversible. Any operation that changes geometry, attributes
     or CRS MUST be undoable, and the operation history MUST be inspectable.
     (Master rule 8.)
R20  Preserve source provenance. Source file, source layer, source entity or
     feature id, original coordinates, original attributes and the
     transformation history travel with every object through the CIR, so a
     conversion can be explained after the fact and reversed. (Master rule 16.)
R21  Every geometry-changing operation is tolerance-aware, and the tolerance is
     an explicit, displayed, unit-labelled setting. No tolerance is hard-coded.
     (Master rules 17 and section 32.)
R22  Export only after validation. Geometry, CRS, attributes, coordinate range,
     encoding and format compatibility are checked before bytes are written, and
     a blocked export states exactly what blocked it. (Master rule 19.)
R23  No secrets in exports. Credentials, tokens and hosted-report keys MUST NOT
     appear in KML, KMZ, project files or exported HTML. Imported HTML and SVG
     are sanitised; every imported file is treated as untrusted. (Master rule 12
     and section 34.)
R24  The first screen stays minimal. Advanced capability is reached through
     contextual panels and the command palette, never by crowding the default
     view. (Master rules 14 and 15.)

Runtime dependencies: ZERO. The shipped extension has no npm runtime package.

in-repo or uses platform APIs (CompressionStream, DecompressionStream,
TextDecoder, DataView, OffscreenCanvas, Web Workers).

Rationale: MV3 forbids remote code; a zero-runtime-dependency package cannot
silently acquire one, and it keeps offline mode provably true.

3. CANONICAL INTERMEDIATE REPRESENTATION (CIR)
================================================================================

3.1 TOP LEVEL
A parsed source becomes exactly one CirDataset:

  CirDataset {
    kind: 'vector' | 'raster' | 'pointcloud' | 'table' | 'mixed'
    name: string
    source: SourceInfo          // filename, size, sha256, detected format
    crs: CrsRef | null          // null means UNKNOWN - never guess
    crsOrigin: 'declared' | 'sidecar' | 'user' | 'inferred' | 'unknown'
    units: LinearUnitId | null
    axisOrder: 'xy' | 'yx' | 'unknown'
    vertical: VerticalRef       // {kind:'unknown'|'ellipsoidal'|'orthometric'|'local'}
    layers: CirLayer[]          // vector/CAD
    raster?: CirRaster
    pointcloud?: CirPointCloud
    table?: CirTable
    warnings: Warning[]
    provenance: Provenance
  }

3.2 VECTOR
  CirLayer { name, geometryTypes[], features: CirFeature[], fields: FieldDef[] }
  CirFeature {
    id, geometry: CirGeometry, properties: Record<string, unknown>,
    sourceLayer, sourceEntity,      // e.g. 'LWPOLYLINE'
    sourceHandle,                   // DXF handle, preserved verbatim
    style?: StyleHint
  }
  CirGeometry - GeoJSON-shaped but with explicit dimension:
    { type: 'Point'|'MultiPoint'|'LineString'|'MultiLineString'|'Polygon'
            |'MultiPolygon'|'GeometryCollection',
      coordinates: Position[]..., dimension: 2|3|4 }   // 4 = XYZM
  Position = [x, y] | [x, y, z] | [x, y, z, m]
  Coordinates are ALWAYS stored in the dataset CRS, in x/y (easting/northing or
  longitude/latitude) order. Axis-order handling happens in readers and writers,
  never in the middle of the pipeline.

3.3 RASTER
  CirRaster { width, height, bandCount, pixelType, noData, geotransform:[6],
              crs, extent, statistics?, bands?: BandData[], hasPixelData: bool }
  hasPixelData=false means "georeference/metadata only". A writer MUST refuse to
  emit a raster product from a metadata-only source.

3.4 POINT CLOUD
  CirPointCloud {
    count, loaded, bounds, scale:[3], offset:[3], pointFormat, versionMajor,
    versionMinor, attributes: PointAttributeFlags,
    points: { x:Float64Array, y:Float64Array, z:Float64Array,
              intensity?:Uint16Array, classification?:Uint8Array,
              returnNumber?:Uint8Array, numberOfReturns?:Uint8Array,
              rgb?:Uint16Array, gpsTime?:Float64Array,
              scanAngle?:Int16Array, sourceId?:Uint16Array },
    decimation: { mode:'none'|'nth'|'grid'|'voxel', factor?, cell? } | null
  }
  Typed arrays only - never arrays of objects. A 40M-point cloud in objects is
  an out-of-memory crash; in typed arrays it is a buffer that transfers to a
  worker for free.

3.5 TABLE (survey coordinate schemas)
  CirTable { columns: ColumnDef[], rows: (string|number|null)[][],
             mapping: ColumnMapping | null, detectedSchema: SurveySchemaId|null }
  ColumnMapping names which column is id/easting/northing/elevation/lat/lon/
  code/description. Mapping is required before a table becomes vector geometry.

3.6 PROVENANCE (attached to every dataset and every conversion job)
  Provenance {
    sourceFile, sha256, sourceFormat, detectionConfidence,
    sourceCrs, targetCrs, settingsSnapshot, engineVersions,
    warnings[], qaResult, startedAt, finishedAt, durationMs
  }

5. INGESTION AND DETECTION
================================================================================

5.1 INPUT METHODS (all mandatory)
  1. Drag and drop of files
  2. Drag and drop of folders (webkitGetAsEntry traversal)
  3. File picker (multiple)
  4. Directory picker where Chrome allows it
  5. ZIP / KMZ archive import
  6. Nested archive extraction (depth limited, see 9.3)
  7. Companion-file grouping (see 5.4)
  8. Mixed-format batch queues
  9. Session restore while the workspace tab lives

5.2 LAYERED DETECTOR (core/detect.ts)
Detection MUST run these layers and combine them into a confidence score:
  L1 extension            weak signal, never decisive on its own
  L2 MIME type            weak
  L3 magic bytes          strong  (e.g. 'PK\x03\x04', 'LASF', 0x0000270A shp)
  L4 header structure     strong  (LAS header length, SHP file length field)
  L5 XML root + namespace strong  (kml, gpx, gml, LandXML, osm)
  L6 JSON shape validation strong (GeoJSON type+geometry keys, TopoJSON arcs)
  L7 binary layout probe   strong  (DBF field descriptor table, TIFF IFD walk)
  L8 text heuristics       medium  (DXF '  0\nSECTION', CSV delimiter+numeric
                                    column profile, PLY 'ply\nformat')
  L9 companion context     medium  (a .shx next to a .shp raises SHP confidence)

  Confidence = weighted sum, clamped 0..1.
  >= 0.90  auto-proceed
  0.60-0.89 proceed but show "Confirm detected format" chip
  < 0.60   BLOCK conversion until the user confirms the format

5.3 DETECTION OUTPUT (shown in the inspector header, verbatim style)
    Detected : DXF Vector Drawing (ASCII)
    Confidence: 98%
    CRS      : not declared - selection required
    Units    : from $INSUNITS = metre
    Geometry : 412 point / 88 line / 31 polygon

  "INFERRED" and "not declared" are required labels. An empty CRS field is a bug.

5.4 COMPANION GROUPING (core/companions.ts)
Group by case-insensitive basename within the same directory or archive folder:
  roads.shp + roads.shx + roads.dbf + roads.prj + roads.cpg -> one SHP dataset
  map.mif + map.mid                                          -> one MIF dataset
  ortho.tif + ortho.tfw + ortho.prj                          -> one raster
  cloud.las + cloud.prj                                      -> one point cloud
Missing mandatory companion (.shx or .dbf for SHP) is a WARNING with an exact
message naming the missing file - never a silent partial read.

5.5 JSON DISAMBIGUATION
A .json file is GeoJSON only if it structurally validates: a FeatureCollection
with a features array, or a bare Geometry/Feature with a known type. Otherwise
it is 'json (unrecognised)' and offered only to the table importer if it is an
array of flat objects.


================================================================================
6. CRS AND GEODESY ENGINE
================================================================================

6.1 REQUIRED CAPABILITIES
  - EPSG:4326 WGS 84 geographic
  - EPSG:3857 Web Mercator
  - UTM zones 1-60, north and south, WGS 84 (EPSG:326xx / 327xx)
  - Bundled EPSG subset with name, datum, projection, unit, axis order
  - Projected <-> geographic transformation both directions
  - Explicit axis-order handling per CRS
  - Local / engineering grid mode (no transformation, units only)
  - Custom CRS via WKT1, PROJJSON or PROJ string entry
  - .prj / .qpj parsing and .prj generation for Shapefile export

6.2 PROJECTION MATH (crs/projection.ts)
Transverse Mercator by the Krueger series, WGS 84 ellipsoid:
  a = 6378137.0, f = 1/298.257223563, k0 = 0.9996
  FE = 500000 m, FN = 0 (north) or 10000000 m (south)
Accuracy requirement: round-trip lat/lon -> UTM -> lat/lon MUST agree within
1e-7 degrees, and E/N -> lat/lon -> E/N within 1 mm, across zones 1..60 and
latitudes -80..+84. This is enforced by tests, not by assertion.

6.3 CRS SAFETY RULES
  - A file's declared CRS always wins over any project default.
  - If CRS is unknown AND coordinate magnitudes are ambiguous, conversion STOPS
    and the user must pick a source CRS. Heuristics may SUGGEST, never decide.
  - Suggestion heuristic (suggest only, label 'INFERRED'):
      |x| <= 180 and |y| <= 90                     -> geographic candidate
      100000 <= x <= 900000 and 0 <= y <= 10000000 -> UTM candidate, zone unknown
      anything else                                 -> local/engineering grid
  - A user-selected CRS is written into provenance with crsOrigin='user'.
  - Datum transformation beyond WGS84-family is an ADAPTER. The UI MUST NOT
    offer a datum shift the engine cannot actually perform.

6.4 INDIAN SURVEY DEFAULTS
UTM zones 42N-47N are pinned to the top of the quick list because they cover
India, and the historic Pakhar/Lohardaga profile (EPSG:32645) is offered as a
saved preset - offered, never forced. There is no global default zone.

6.5 VERTICAL
Z is carried, never reinterpreted. verticalReference is one of
ellipsoidal | orthometric | local RL | unknown, defaulting to unknown.
Orthometric<->ellipsoidal conversion requires a geoid model: ADAPTER, and until
it exists the UI MUST NOT offer it.

7. UNITS
================================================================================

7.1 SUPPORTED
  linear : mm, cm, m, km, in, ft (international), us-ft, yd, mi, nmi
  angular: degree, radian, gon
  area   : m2, ha, acre, ft2, km2
  volume : m3, ft3, yd3

7.2 RULES
  - Linear, angular, area and volume are separate namespaces in the UI and in
    the code. An area factor can never be applied to a coordinate: the unit
    engine refuses cross-namespace conversion at the type level.
  - us-ft = 1200/3937 m exactly. int-ft = 0.3048 m exactly. These MUST NOT be
    conflated; a 2 ppm error over a 10 km traverse is 20 mm.
  - DXF $INSUNITS is read on import and written on export.


================================================================================
8. GEOMETRY, TOPOLOGY, PRECISION
================================================================================

8.1 GEOMETRY OPERATIONS
point, multipoint, line, multiline, polygon (with interior rings), multipolygon,
geometry collection where the target permits, Z always, M where supported.

8.2 CURVE POLICY (CAD -> GIS)
ARC, CIRCLE, ELLIPSE and SPLINE MUST be segmentized with an explicit, visible
tolerance (default: sagitta 0.01 m, minimum 8 segments per full circle).
The segment count and the tolerance used are recorded per entity in the QA
warnings. Silent chord replacement is prohibited (R3).
The original entity type and handle are preserved in feature properties as
_srcEntity and _srcHandle.

8.3 TOPOLOGY CHECKS (qa/topology.ts)
self-intersection, duplicate vertices, zero-length segments, unclosed rings,
ring orientation, duplicate features, invalid holes, overlapping polygons.

8.4 REPAIR
remove duplicate vertices, close rings, snap within tolerance, fix trivial
self-intersections, normalise ring orientation, deduplicate features.
DEFAULT: ALL REPAIR OFF. Survey data is legal evidence; the tool does not
quietly edit it. Enabling repair is a deliberate user action and is recorded.

8.5 PRECISION
Internal storage is IEEE-754 double, always. Display rounding is presentation
only and MUST NOT feed back into computation. Output precision options: full |
3 | 4 | 5 | 6 | custom. Default 3 decimals for human-readable projected output,
full precision for geographic output (1e-9 deg) and for binary formats.
QA reports the maximum coordinate delta introduced by output rounding.


================================================================================
9. ENGINE IMPLEMENTATION NOTES
================================================================================

9.1 DXF READER (engines/cad/dxf-read.ts)
Group-code tokenizer, then section walk: HEADER, TABLES (LAYER), BLOCKS,
ENTITIES. Required entity coverage:
  POINT, LINE, POLYLINE (2D/3D + vertex stream), LWPOLYLINE, 3DFACE, SOLID,
  TRACE, ARC, CIRCLE, ELLIPSE, SPLINE, TEXT, MTEXT, INSERT (block expansion
  with translation/scale/rotation), ATTRIB, DIMENSION (anchor point + text),
  LEADER, MLEADER (polyline path), HATCH (boundary paths), MESH/POLYFACE
  (as faces where present).
Header values consumed: $INSUNITS, $EXTMIN/$EXTMAX, $ACADVER.
Every entity type encountered but not converted is COUNTED BY NAME and reported
(dxfUnconvertedEntities behaviour from Geo-Studio is preserved and extended).
Layer name, colour (ACI + true colour), linetype, elevation and handle are
preserved into feature properties.

9.2 DXF WRITER (engines/cad/dxf-write.ts)
Emit AC1015 (R2000) minimum, with an option for AC1032 (2018). Mapping:
  Point   -> POINT (with optional TEXT label)
  Line    -> LWPOLYLINE (2D) or POLYLINE with 3D vertices when Z is preserved
  Polygon -> closed LWPOLYLINE (+ optional HATCH fill)
  Text    -> TEXT or MTEXT
Layer per source layer, or per attribute field (layer-by-code), selectable.
The writer MUST write $INSUNITS matching the export unit.

9.3 ARCHIVES (engines/archives/zip.ts)
Read: local-header walk plus central-directory walk, store + deflate, using
DecompressionStream('deflate-raw').
Write: CompressionStream('deflate-raw') with a pure-TS fixed-Huffman fallback
(ported from Geo-Studio zip.ts) so the writer never depends on a flag.
Security limits, all enforced:
  max nesting depth            4
  max total decompressed size  2 GB (configurable, default 1 GB)
  max compression ratio        200:1 per entry (zip-bomb guard)
  path traversal               entries containing '..' or absolute paths are
                               rejected, not sanitised
  no execution                 archive contents are never evaluated

9.4 LAS (engines/pointcloud/las.ts)
Reader: public header block (1.0-1.4), variable-length records, point formats
0-10, scale/offset applied as x = X*scaleX + offsetX in double precision.
Header/file-length cross-check: if declared point count exceeds the bytes
available, report "declares N records, file holds M" and stop - do not read
garbage.
Writer: LAS 1.2/1.4, point formats 0/1/2/3/6/7, computed scale/offset from the
data bounds unless the user pins them, correct bounding box, correct
"number of points by return".
LAZ: header says compressed (point format bit 7 set / laszip VLR present) ->
reject with the exact reason. Never fall through to the LAS reader (R5).

9.5 SHAPEFILE (engines/vector/shapefile.ts)
Reader: .shp record loop, shape types 1/3/5/8/11/13/15/18/21/23/25/28 (point,
polyline, polygon, multipoint, and their Z/M variants), .dbf field table with
C/N/F/D/L types and code-page from .cpg, ring orientation to decide outer vs
hole, .prj through the WKT parser.
Writer: emits .shp + .shx + .dbf + .prj + .cpg packaged as one ZIP.
DBF constraints enforced before writing: field name <= 10 bytes uppercase,
unique after truncation, numeric width <= 18, text width <= 254. Every rename
and truncation is reported and recorded in the manifest (33 in the source spec).
Shapefile cannot hold mixed geometry types: the writer splits by type into
name_point / name_line / name_polygon and says so.

9.6 SURVEY TABLES (engines/survey/schema.ts)
Header-name matching plus positional fallback. Recognised aliases (case- and
separator-insensitive), preserving the ORIGINAL field names in the output:
  id     : point, pt, pointid, pt_no, no, id, name, station, stn
  easting: easting, east, e, x, x_coord, utm_e
  northing: northing, north, n, y, y_coord, utm_n
  elev   : elevation, elev, z, rl, level, height, ht
  lat    : latitude, lat, y_lat
  lon    : longitude, lon, lng, long, x_lon
  code   : code, feature, desc, description, remark, remarks, layer
  mining : bhid, hole_id, borehole, bench, crest, toe, pit, block, plot,
           khasra, khewat, khatian, lithology, assay, grade
Positional schemas: PNEZD, PENZD, NEZ, ENZ, XYZ, ID-X-Y-Z, ID-Y-X-Z.
The user can always override the mapping in a preview table. Coordinate order
is ALWAYS shown explicitly; latitude and longitude are never swapped silently.

9.7 GEOTIFF (engines/raster/geotiff.ts, geotiff-write.ts, tiff-codec.ts)
Structure: TIFF/BigTIFF IFD walk, ModelPixelScale, ModelTiepoint,
ModelTransformation, GeoKeyDirectory (EPSG code extraction), sample format,
bits per sample, band count, nodata, predictor, planar config, tile/strip
layout.

Pixel decode (tiff-codec.ts, kept separate from TIFF structure so each codec is
testable against a spec vector without a TIFF around it):
  compression   uncompressed, LZW, Deflate (codes 8 and 32946), PackBits
  predictors    2 horizontal differencing, 3 floating point
  layout        strips and tiles, planar configurations 1 and 2
  samples       1/2/4/8/16/32/64-bit unsigned, 8/16/32/64 signed,
                16/32/64-bit float, little and big endian
  bands         decoded into Float64Array per band, row-major, top row first
  ceiling       MAX_SAMPLES bounds an in-browser decode; beyond it the refusal
                names the size and the crop command rather than crashing

NOT implemented: JPEG, JPEG 2000, LERC, WebP and Zstandard compression, and
multi-IFD pyramids (only the first image of a file is read).

Two details that decide correctness, both regression-tested:
  - LZW "early change". The decoder cannot add a table entry until it has read
    the code after the one the entry describes, so at any moment its table holds
    one entry fewer than the encoder's did. The encoder widens 9->10 bits after
    adding entry 510; the decoder must therefore widen when its own next free
    code reaches 510, not 511. Matching the encoder's threshold decodes the
    first few hundred pixels correctly and then shifts every later code by one
    bit - a raster that looks like plausible terrain and is not.
  - Predictor 3 is not horizontal differencing over floats. The encoder splits
    each row into byte planes (all high bytes, then all second bytes, ...) so
    that the near-identical exponent bytes of neighbouring elevations group and
    compress. Reversing it is two steps: accumulate the byte deltas, then
    de-interleave the planes. Skipping the second step yields NaN and absurd
    values.

An LZW code beyond the next free table entry is corrupt and stops the decode.
Accepting it would store a forward reference in the prefix chain, and walking
that chain would never terminate: a corrupt strip must not be able to hang the
conversion worker.

A file whose compression is not bundled is NOT a failed read. Pixels are
refused by name, hasPixelData stays false, and the georeference, extent,
statistics and footprint that were readable are still returned - losing those
as well would serve nobody (R1, R2).

Writing (geotiff-write.ts): single IFD, little-endian, strip-based, chunky
planar, no predictor, no BigTIFF - the settings every GIS package reads without
complaint. Deflate by default, uncompressed available. The sample type is
chosen from the data so that no value is silently rounded: integers stay
integers, fractional values become float32, and values beyond float32's exact
range keep float64; nodata participates in that choice, because picking uint8
for data that fits it would clamp a -9999 nodata cell to zero and turn holes
into sea level. An explicitly chosen narrower type is honoured but reports the
counts of clamped and rounded pixels (R3). Rotated georeference is reported and
not written, because ModelPixelScale/ModelTiepoint describe an axis-aligned
raster only.

9.8 ASCII GRID (engines/raster/asciigrid.ts)
Full read and write of ncols/nrows/xllcorner|xllcenter/yllcorner|yllcenter/
cellsize/NODATA_value plus the value matrix. This is the working DEM path and
is where DEM round-trip tests run.

10. QA / FIDELITY ENGINE

10.1 CONTRACT
QA is a re-import comparison, not a success message. After writing the output,
the engine parses the produced bytes back into a CIR and compares.

10.2 VECTOR CHECKS

10.4 RASTER CHECKS

  PASS WITH WARNINGS   re-imported, known and enumerated losses
  FAILED               re-import failed or a check exceeded tolerance

12. BATCH, PACKAGING, NAMING
================================================================================

12.1 BATCH
Per-file target or one global target. Apply-to-selected. Retry failed, skip
completed, pause, resume, cancel. Per-file and overall progress with ETA.
Error isolation: one failed file never aborts the batch.
Concurrency defaults to min(4, hardwareConcurrency) and is user-settable.

12.2 OUTPUTS
Single file downloads directly. Multi-file targets (Shapefile, MIF/MID, KMZ)
are packaged automatically. A batch produces one master ZIP plus a manifest.

12.3 MANIFEST (CSV and JSON, both)
source filename, source format, detection confidence, target filename, target
format, source CRS, target CRS, feature/point/pixel counts in and out, output
size, status, warnings, errors, engine versions, sha256, timestamp, duration.

12.4 FILE NAMING
Default {basename}_converted_to_{target}.{ext}
Alternatives {basename}_{target} and {basename}_{date}_{target}
Unsafe path characters are sanitised. The source is never overwritten.

12.5 DELIVERY STRUCTURE (rule R16 - core/layout.ts)
The layout engine plans and packages; it never writes format bytes. That split is
what makes structure testable on paths alone (tests/structure.test.ts asserts on
strings like "Mine/Infrastructure/Haul road.geojson").

Three layouts, user-selectable per conversion, in the settings panel beside
precision because it is a first-class choice and not an advanced one:

  single         One output file. The obvious case stays obvious.
  per-layer      One file per CIR layer, placed in folders that reproduce the
                 layer hierarchy: layer path ["Mine","Infrastructure"] becomes
                 Mine/Infrastructure.<ext>. Several files are packaged as one ZIP
                 whose folders ARE the hierarchy.
  mirror-source  As per-layer, but rooted at the source's own directory and
                 archive nesting. A file read from survey.zip!Delivery/plots.dxf
                 is delivered under survey/Delivery/.

Invariants the layout engine must hold:
  - A single layer gets no folder. One output file is never wrapped in a ZIP.
  - Path segments are sanitised, so a layer named "../etc" cannot escape the
    delivery root.
  - Colliding paths get numeric suffixes rather than overwriting each other.
  - Multi-file targets (Shapefile, MIF/MID) return LOOSE grouped members, not a
    nested ZIP. The layout engine decides folder placement, so a shapefile inside
    a batch delivery is Borehole/Borehole.shp, not a ZIP inside a ZIP.
  - A batch mirrors the input folder tree when mirrorBatchTree is on (default).

Hierarchy across a format hop: GeoJSON carries the layer path in the feature
property _layer, joined with " / ". The GeoJSON reader regroups on it, so
DXF -> GeoJSON -> KML rebuilds nested KML folders instead of one flat layer.

The full delivery tree is computed before packaging and shown in the workspace's
"Delivery structure" tab, so the user sees the folder layout before downloading.

13. NATIVE MESSAGING HOST (DWG / ODA)
================================================================================

13.1 WHY
A Chrome extension cannot execute a native converter. DWG therefore runs through
Chrome Native Messaging to a small local host that drives the user's own
installed ODA File Converter. This reuses the prototype's proven flow.

13.2 PROTOCOL (stdio, 4-byte little-endian length prefix + UTF-8 JSON)
  Request  { id, op: 'ping'|'health'|'convert', payload }
  convert  payload { sourceName, sourceBase64, targetFormat, odaVersion }
  Response { id, ok, result?, error?, engine: {name, version, path} }
  Progress { id, progress: 0..1, stage: string }

13.3 HOST BEHAVIOUR (native-host/universal_bhunex_host.py)
  - creates an isolated temp job directory per request, always cleaned up
  - validates that the payload is a DWG by magic bytes ('AC10'..'AC10xx')
  - invokes ODA File Converter exactly as the prototype did:
      <exe> <inDir> <outDir> <ACADxxxx> DXF <recursive> <audit> *.DWG
  - enforces a timeout and returns stderr/stdout on failure
  - validates the produced DXF (non-empty, contains 'SECTION')
  - never touches a path outside its own temp directory
  - reports engine name, version and executable path in every response

13.4 STATUS STATES (shown in the top bar)
  READY | NOT INSTALLED | CONFIGURATION ERROR | ENGINE ERROR | TIMEOUT
The extension is fully functional for all non-native formats in every state.
When the helper is absent, DWG cards show "Native Engine Required" and the
convert button for DWG is disabled with a link to docs/NATIVE_HOST.md.

13.5 INSTALLERS
native-host/install-windows.ps1, install-macos.sh, install-linux.sh write the
native messaging manifest into the correct per-platform location with the
extension ID supplied by the user at install time.

14. PERFORMANCE AND MEMORY
================================================================================

14.1 WORKERS
  parse worker    detection + reading -> CIR
  convert worker  CIR -> target bytes
Anything above WORKER_THRESHOLD_BYTES (2 MB, from Geo-Studio's parseClient)
goes to a worker. Transferable ArrayBuffers are used for payload hand-off;
typed arrays are never structure-cloned repeatedly.

14.2 TARGETS (measured by the perf test, not claimed)
  < 10 MB vector      interactive, < 1 s to inspector
  10-100 MB           worker path, UI stays responsive, progress visible
  > 100 MB            chunked/streaming where the engine allows, otherwise the
                      pre-flight refuses with an actionable message

14.3 PRE-FLIGHT
Before a risky job, estimate memory (bytes x engine expansion factor) against
navigator.deviceMemory / performance.memory where available. If it exceeds the
budget, refuse with:
  "This dataset is too large for in-browser processing (estimated 3.4 GB peak).
   Use the local engine, or crop/decimate/filter the dataset first."

14.4 REPORTED METRICS
read speed, conversion speed, output size, elapsed time, peak memory estimate.

14.5 ALGORITHM SELECTION BY DATASET SIZE (STATUS: PARTIAL - the index is built)
The engine picks the strategy; the user never has to know which:
  small       direct geometry operations
  medium      indexed spatial queries (R-tree or equivalent)
  large       tiling, chunking, streaming
  very large  progressive visualisation and selective processing
Spatial indexing is not needed by format conversion: a reader walks its input
once. It became necessary the moment topology and overlap detection arrived,
because each is a pairwise query that is quadratic without one - 40,000 parcels
is 800 million comparisons unindexed and a few hundred thousand indexed. It
therefore landed in the same phase as the first feature that needed it, not
before.

core/spatial-index.ts is a uniform grid, not an R-tree, deliberately: it
bulk-loads in one pass with no balancing, so it is cheap enough to build per
check rather than maintain across edits; and its behaviour stays predictable
when boxes overlap heavily, which is exactly what cadastral parcels and contour
lines look like. A feature far larger than the rest goes in an oversized list
scanned on every query - correct, and slower only for the few that deserve it.

Tiling and streaming for very large datasets remain open.

22. FIDELITY PREDICTION AND THE CONVERSION CENTRE
================================================================================
STATUS: BUILT (core/predict.ts, tests/predict.test.ts). PARTIAL for the report
document itself, which is still the batch manifest rather than a per-file page.

Loss is now stated BEFORE a conversion runs, so the engineer chooses a target
with the cost in view rather than discovering it in the QA report afterwards.

22.1 PROVENANCE (R20)
Every CIR object carries: source file, source layer, source entity/feature id,
original coordinates, original attributes, and an ordered transformation log.
Partly built - sourceLayer, sourceEntity and sourceHandle already survive a
DXF -> GeoJSON -> DXF round trip. Still missing: original coordinates retained
alongside transformed ones, and the per-object transformation log.

22.2 THE PREDICTION (BUILT)
Given (source CIR, target format) compute, without converting:
  geometry compatibility     curves, 3D, M, multipart, geometry collections
  attribute compatibility    field count, name length, type width, encoding
  CRS compatibility          transform available, datum shift required
  Z compatibility            target stores Z at all
  style / label compatibility
  layer compatibility        hierarchy expressible, or flattened to folders
  precision risk             target's numeric width vs the data's range
  unsupported entity risk    counted by entity type
  topology loss risk
  metadata loss risk

Every axis resolves to GREEN (faithful), YELLOW (partial), or RED (loss), and
every non-GREEN axis MUST name the count and the entity or field involved.

Two design decisions carry this section:

  ONE PASS, MANY TARGETS. profileDataset() walks the features once and produces
  a DatasetProfile; predictFromProfile() compares that profile against a format.
  Ranking thirty candidates therefore costs one pass, not thirty. It is also
  what lets the worker profile a dataset where the full CIR lives and hand the
  UI something it can predict from - the UI only ever receives a truncated
  feature preview, so predicting there would report counts that are quietly
  wrong, which is worse than reporting nothing.

  THE REGISTRY HOLDS THE LIMITS. FormatLimits carries what the capability
  booleans cannot express: DBF's 10-character field names and 254-byte values,
  shapefile's one-shape-type-per-file, GeoJSON's mandated EPSG:4326, GPX's
  point-and-line-only geometry, each format's layer model, whether style and
  labels survive. Putting them in the registry rather than the predictor keeps
  one source of truth about what a format can hold (R1).

A finding that cannot name its subject is not raised. "Some attributes may be
truncated" teaches users to ignore the panel; "3 field names exceed DBF's
10-character limit: sample_description -> sample_des, collar_elevation ->
collar_ele" is something a surveyor acts on, because it is exactly the silent
break that ruins a downstream join weeks later.

Precision is graded by GROUND DISTANCE, not by decimal count. Three decimals of
a metre is a millimetre and passes silently; three decimals of a degree is about
111 m and is reported. The same number means entirely different things, and a
predictor that reported "3 decimal places" for both would be useless.

22.3 "SHOW EXACTLY WHAT WILL BE LOST" (BUILT)
A workspace tab - not a modal - listing every predicted loss as a countable
statement -
"17 ARC entities will be densified at 0.01 m sagitta", "field
`sample_description` will be truncated to 10 characters in DBF" - with the
the axis grid above it, so "geometry is fine, only attributes suffer" is
readable without going through every row. It is a tab rather than a modal
because choosing a format IS the comparison: the user sits in it and switches
targets. The format cards each carry the verdict for the selected data, and the
list is ordered by it (spec §25.3).

Export validation (R22) runs the same engine, in the pipeline, before any writer
is called: an impossible target fails immediately with a reason instead of
failing halfway through a batch with a writer-level error.

WHAT BLOCKS AND WHAT DOES NOT. Only genuine impossibility blocks: a target this
build cannot write, an adapter whose engine is absent, a data-kind pairing no
engine bridges. A RED finding is a LOSS, and loss does not block - it is a cost
the engineer is entitled to accept, and refusing it would be this tool deciding
what someone may do with their own data. Predicted losses are raised as warnings
up front so they sit in the same list as the ones writers report afterwards.

22.4 CONVERSION REPORT
Source (name, format, size, CRS, units, layers, feature count), processing
(transformations, repairs, edits, warnings), output (format, CRS, counts),
fidelity per axis, and QA (errors, warnings, repaired, unresolved). The batch
manifest already carries most of these fields; the per-conversion report is the
same data rendered for one file.

23. GEOMETRY QA, TOPOLOGY AND SPATIAL RELATIONSHIPS
================================================================================
STATUS: BUILT (qa/defects.ts, qa/rules.ts, tests/qa.test.ts). The canvas
interaction that lets a user click a defect and see it is Phase 11.

23.1 DEFECT CATALOGUE
qa/topology.ts checks a feature against ITSELF - unclosed rings, duplicate and
consecutive-duplicate vertices, zero-length segments, ring orientation,
self-intersection, duplicate features.

qa/defects.ts checks features against EACH OTHER, which is where cadastral and
mine-survey data actually goes wrong. Built: sliver polygons, spikes, bow-ties,
hole outside shell, Z anomalies, polygon overlaps, shared-edge mismatch, nested
polygons, near-duplicate geometry, crossing lines, dangling endpoints.

Three rules govern every detector:

  LOCATABLE. Severity, layer, feature id and a position. A defect the user
  cannot go and look at is a statistic, not a finding.

  NAMES ITS TOLERANCE. "These parcels overlap" is meaningless without "by more
  than 0.01 m". A millimetre is survey noise; a metre is a boundary dispute. The
  threshold is stated in the finding and is always the user's to set (R21).

  DETECTS ONLY. Detection and repair are separate modules so that a scan can be
  run for information alone, and so a legally operative boundary can be
  inspected without being touched (R18).

Three implementation decisions worth keeping:

  Slivers are found by THINNESS, not by area. The Polsby-Popper ratio
  4*pi*area/perimeter^2 is 1 for a circle and near 0 for a strip. A 0.2 sq m
  survey monument pad is small and valid; a 0.2 sq m strip 40 m long is an
  artefact. Testing area alone flags every small legitimate parcel.

  Z anomalies use the MEDIAN and MEDIAN ABSOLUTE DEVIATION, not the mean and
  standard deviation. A single transposed decimal - 4123.45 for 412.345 -
  inflates the standard deviation so far that it drags the threshold past
  itself and goes unreported. That masking effect defeats the exact blunder the
  check exists to catch.

  Shared-edge mismatch is measured VERTEX TO SEGMENT, not vertex to vertex. The
  usual case is one parcel carrying an extra vertex that bulges a few
  millimetres into the other's straight edge; there is no opposing vertex near
  it, so a vertex-to-vertex test finds nothing and the sliver survives to the
  dissolve.

Pairwise checks run through core/spatial-index.ts. Above maxPairwiseFeatures
they are REFUSED with the count and the reason - never silently reduced to a
subset that reports a clean result which is not.

23.2 CONFIGURABLE TOPOLOGY RULES (BUILT - qa/rules.ts)
Must not overlap; must not have gaps; must contain; must be within; must touch;
must be covered by; must not self-intersect; shared boundaries must match;
lines must connect; polygons must close.

A rule differs from a defect: a defect is a suspicion a heuristic raises, a rule
is a standard the USER asserts, so a violation is a failure against their stated
intent. Both are reported; only rules can be said to pass or fail.

Scope is part of every rule: whole dataset, one layer, or named features. A
surveyor fixing one disputed boundary runs "must not overlap" on that parcel and
gets two violations, not four thousand. Forcing whole-dataset evaluation is how
tools push people into global repairs they never wanted (R18).

A rule that CANNOT be evaluated - a relational rule with no second layer, an
empty scope - reports notEvaluated with the reason. It MUST NOT report "passed":
a rule that did not run has not been satisfied.

"Must not have gaps" finds gaps along adjacent boundaries. It does NOT find an
entire missing parcel inside a coverage, which needs a boolean union this build
does not have, and the violation text says so rather than implying wider cover.

23.3 OVERLAP AND GAP INTELLIGENCE
Classify each pair: overlaps, contains, touches, crosses, separated, gap.
For cadastral parcels additionally detect duplicate boundaries and shared-edge
mismatch, and propose the most conservative correction.
Legal boundaries are never modified without explicit per-operation confirmation
(R18).

24. GEOMETRY REPAIR
================================================================================
STATUS: BUILT for the preview/apply/undo contract and six operations
(qa/repair.ts). The remaining operations in 24.2 are Phase 11, and they inherit
the contract rather than reinventing it.

24.1 THE CONTRACT
qa/topology.ts repairs as part of a CONVERSION: switch an option on and the
pipeline applies it. That is the wrong shape for editing. qa/repair.ts splits
every operation in two:

  planRepair(dataset, operation, scope)  -> RepairPlan   nothing is modified
  applyRepair(dataset, operation, scope) -> RepairResult new dataset + undo

Both call the SAME rewrite function - the preview is literally the apply, run
without keeping the result. There is no second code path that could describe one
thing and do another, which is how preview features usually become lies.

A plan lists every change with its feature, its position and the distance moved,
so "close rings" can be inspected before it touches a boundary.

UNDO IS A DIFF, NOT A SNAPSHOT (R19). Only the features that actually changed
are held, each as its geometry before the edit. A layer of 400,000 contours
where one ring was closed costs one stored geometry, not 400,000 - the
difference between undo working and undo running the tab out of memory.

PROTECTED LAYERS. A layer named in protectedLayers is refused, with the refusal
reported and counted, never silently skipped. Cadastral and lease boundaries are
legally operative: moving one is a change to a title, not a data fix (R18).

Built: close rings, remove duplicate vertices, remove zero-length segments, fix
ring direction, remove spikes, snap vertices within a feature.

24.2 SPECIFIED (Phase 11)
Snap shared edges across features; regularise; smooth; simplify; densify;
repair self-intersection; remove slivers; merge adjacent polygons; split
polygon; split line; extend, trim and join lines; make and explode multipart;
fill and remove holes; rebuild topology.

Every operation: previewable before commit, tolerance-aware with the tolerance
displayed in the data's own units (R21), undoable (R19).

24.3 FIX ALL SAFE ISSUES (BUILT)
Safe means two things at once: reversible, AND incapable of moving a boundary
beyond a stated tolerance.

Ring closure qualifies only when the gap is small enough to be a digitising slip.
A ring left half a metre open is a question for the surveyor, and the refusal
says so rather than quietly shutting it.

SNAPPING IS NEVER INCLUDED. Snapping moves survey positions; on cadastral data
that is a legal act, not a tidy-up. Protected layers are never touched. Every
operation applied and every one skipped is listed with its reason.

27. LABEL AND ATTRIBUTE BURN-IN, CAD POLYGONISATION
================================================================================
STATUS: BUILT (qa/burn-in.ts, qa/label-placement.ts, qa/polygonize.ts,
tests/burnin.test.ts). Both stages are wired into the pipeline as opt-in
settings, so they apply to what is actually written and work at any file size.

27.1 THE PROBLEM
A cadastral DXF typically holds plot boundaries on one layer and plot numbers as
TEXT or MTEXT on another. The association between them is spatial and implicit.
Exported naively, the polygons arrive unlabelled and the text arrives as
detached points - which is why CAD-to-GIS cadastral conversion is usually redone
by hand.

27.2 DETECTION AND MODES (BUILT)
Detect points, TEXT, MTEXT, block text and attribute labels inside polygons.
A candidate inside a HOLE belongs to no parcel and is reported as an orphan
rather than attached to the ring that surrounds the hole.

The text is read from the property names this project's own DXF reader writes
(`_text`, `_textHeight`) before the GIS-style names. A burn-in engine that only
understood `text` would find nothing in the CAD files it exists for - which is
exactly what the end-to-end test caught.

Then offer:
  A ATTRIBUTE burn-in   text content becomes a polygon attribute
  B LABEL burn-in       a label representation bound to the polygon
  C GEOMETRY burn-in    a permanent text feature placed inside the polygon
  D CAD burn-in         CAD-compatible annotation
  E KML/KMZ burn-in     polygon name and description for Google Earth

When several candidates fall inside one polygon: nearest to centre, largest
text, first found, concatenate, or a named attribute field. Every rule is
DETERMINISTIC - the same input must always yield the same plot number - and the
concatenate rule sorts before joining so the result does not depend on read
order.

AMBIGUITY IS REPORTED, NOT RESOLVED SILENTLY. The rule that picked the winner is
named in the report and every rejected candidate is listed with the reason it
lost. A wrong plot number attached confidently is far worse than one the user
was asked about.

The source point or text is NEVER deleted unless the user explicitly chooses
"replace source" (R17, R18).

27.3 LABEL PLACEMENT (BUILT - qa/label-placement.ts)
The anchor is the POLE OF INACCESSIBILITY: the interior point furthest from any
edge, found by the quadtree search polylabel uses - subdivide, keep the cell
whose upper bound on distance is best, stop when the bound can no longer beat
the best point found.

Not the centroid, and this is the whole point of the module. The area centroid
of a C-shaped parcel, a river bend or a lease wrapped around a pit falls OUTSIDE
the polygon, so the plot number lands in the neighbouring plot. On cadastral
output that is not cosmetic: it mislabels someone's land. Holes are handled too,
so a label never lands in an exclusion.

The search returns CLEARANCE - the distance to the nearest edge - for free,
which is the label's usable half-width. A label wider than that is still placed
but reported as overflowing: suppressing it silently would lose the plot number.

Narrow polygons (clearance below a fraction of the longer extent) rotate to
follow the longest edge, kept upright so the text stays readable.

Collisions are resolved by clearance: the label with the most room keeps its
position, and a label that cannot be placed without overlapping is SUPPRESSED
rather than nudged. A plot number a few metres into the neighbouring parcel is
worse than one the user can see is missing.

27.4 CAD CLOSED-BOUNDARY POLYGONISATION (BUILT - qa/polygonize.ts)
The DXF reader already turns a CLOSED polyline into a polygon. This handles the
rest: boundaries drawn as separate LINE entities, assembled end-to-end into
loops; boundaries that nearly close, within a stated tolerance; and loops inside
loops, resolved into shells and holes.

The tolerance discipline matters more here than anywhere else in the tool.
Closing a 3 mm gap recovers the draughtsman's intent; closing a 3 m gap invents
a boundary. So the gap closed is recorded per polygon as _polygonized_gap,
nothing is closed beyond the tolerance the user set, and a boundary that will
not close is returned as an OPEN LINE with the gap that defeated it - never
quietly forced shut (R18, R21).

Provenance survives: _polygonized_from lists the entity handles the polygon was
assembled from, and _polygonized_segments how many (R20).

DELIBERATE LIMIT: lines that cross in their INTERIORS are not noded. Crossing
lines are a defect that qa/defects.ts reports; silently noding them here would
build polygons out of geometry the user has not been told is broken.

ORDER IN THE PIPELINE: polygonise runs before repair and before burn-in. Repair
should act on the polygons that will actually be exported, and burn-in needs
polygons to put text inside.

28.1 BOREHOLE AND MINING MODEL (BUILT)
A borehole never arrives as one thing: the collar is a point (hole id, easting,
northing, RL, depth, azimuth, dip) and the geology is a separate table of depth
intervals keyed by hole id. Two files, joined by a column, and every mining
package spells the columns differently.

engines/survey/borehole.ts recognises both shapes and joins them by hole id
ACROSS layers and across a table that was never converted to points, because
that is how the data actually arrives. Column aliases cover Datamine, Surpac,
Micromine, Vulcan and spreadsheet naming; assay columns are recognised by
element symbol and grade suffix.

Three rules:
  - Thickness is COMPUTED from the depths, never read from a thickness column.
    Sources routinely carry a stale one that disagrees with its own from/to,
    and the depths are the measurement.
  - An interval whose hole id matches no collar is reported as ORPHANED, never
    attached to the nearest hole. A log against the wrong borehole is worse
    than a log the user is told is unmatched (R2).
  - checkLogContinuity finds gaps and overlaps: a gap means a missing interval,
    an overlap means two records claim the same metre and one is wrong. Both
    are common in hand-compiled logs and invisible from the table.

28.2 STYLED KML/KMZ ENGINE (BUILT for balloons; overlays still open)
Built: nested folders (R16), placemarks, geometry, line and polygon styles,
altitude modes, and HTML description balloons from a template.
Specified: icons, transparency control, ground and screen overlays, NetworkLink.

BOREHOLE CORE-LOG BALLOON (BUILT). Collar header, then the interval table, then
any continuity problem found. Only the columns that carry data are emitted: an
empty RQD column on every row of a sixty-interval log pushes the lithology
off-screen. The continuity warnings sit BESIDE the log rather than in a separate
report, because the balloon is where a geologist actually looks at the hole.

THREE SAFETY RULES, all tested:
  - EVERYTHING IS ESCAPED. Values come from files this tool did not write and
    the output is HTML rendered in someone else's viewer. The balloon is
    assembled from a fixed skeleton and no source text can become markup.
  - NO SECRETS LEAVE. Property names and values that look like credentials are
    dropped before rendering, a signed report URL is refused, and the omission
    is REPORTED as a warning - a silent drop would be its own dishonesty. A KMZ
    is emailed around; a token inside one has leaked (R3, R23).
  - The CDATA terminator is escaped inside balloon content, so a value
    containing "]]>" cannot close the section early and corrupt the file.

Styling is inline: Google Earth strips a <style> block in some versions and
ignores external stylesheets entirely. Colours hold contrast on both the light
and dark balloon backgrounds.

28.3 PDF AND IMAGE MAP GEOREFERENCING
Render a scanned map at its true aspect ratio; zoom, pan, place, crop, rotate.
2, 3 and 4-point georeferencing with GCP entry, residuals and RMS error, affine
transformation, and higher-order only where the control geometry justifies it.
An image MUST NOT be described as georeferenced without actual reference
information (R2).

28.4 GEOREFERENCING PANEL (PARTIAL)
Built: QGIS GCP point files read and written; world files read and written.
Specified: the panel itself - GCP table, canvas, coordinate entry, residuals,

28.5 KML/KMZ TEMPLATE SYSTEM (BUILT for field ordering; branding still open)
Templates: plain, cadastral, survey, borehole, mining, contour. A template

29. SPATIAL INTELLIGENCE LAYER
================================================================================
STATUS: SPECIFIED. Phase 9.

29.1 DETERMINISTIC FIRST
Every statement the intelligence layer makes MUST come from a deterministic
spatial computation, and MUST be explainable by naming the features and the
threshold that produced it. Examples, all computable:
  "42 polygons overlap by more than the 0.01 m tolerance."
  "18 polygons contain text labels."
  "12 CAD boundaries are closed to within 0.05 m but not closed."
  "Coordinates look UTM-like but no CRS is declared."
  "The selected target would lose Z on 1,204 features."
  "7 labels would collide after export at this scale."
  "Layers PLOT and PLOT_2 have identical geometry."
  "Point codes match a borehole collar pattern."
  "Fields E, N, RL look like Easting/Northing/Reduced Level."
  "From/To fields look like geological intervals."

It suggests; it never edits. No statistical or generative model may modify
engineering data (R18).

29.2 PROJECT HEALTH
A single score from CRS certainty, geometry validity, topology, duplicate data,
missing attributes, conversion risk and unresolved warnings - always expandable
into the exact contributing items. A score with no drill-down is decoration.

30.1 TWO CANVASES (BUILT - ui/dual-canvas.ts)
LEFT: import/source. RIGHT: export/target, showing the actual converted
representation before export. Both support pan, zoom, fit-to-data, coordinate
readout, layer control, selection, measurement, visibility and render
diagnostics.

A draggable vertical divider; either side maximisable; when one collapses the
other takes the space. Pan, zoom and extent synchronise, and can be unlinked.

Nobody should have to export a file to discover that the conversion damaged it.

30.2 VISUAL DIFF (BUILT - qa/diff.ts for the numbers, qa/geometry-overlay.ts
for where they are, drawn over both canvases)
Ten axes: feature count, geometry types, vertex count, coordinates, area,
perimeter, extent, attributes, CRS and Z range. Each reports the source value,
the output value, the measured difference and the tolerance it was judged
against, in the data's own units:
  Area   100.00 sq units -> 100.01 sq units; difference 0.01 sq units. PASS

The NUMBER is the deliverable. A surveyor signing off cannot tell from "PASS"
whether a difference is rounding or a defect, and a dump of every coordinate
tells them nothing at all.

Computed from the SAME re-import the QA verdict uses, not by reading the output
a second time, so the verdict and the numbers beside it can never describe
different bytes.

Three behaviours worth keeping:
  - Coordinate drift is reported only when the vertex counts match. Without a
    correspondence there is no drift to measure, and reporting one anyway would
    be a number that means nothing. It says so instead.
  - Holes SUBTRACT from the area. A parcel with a 200 sq m exclusion is not
    200 sq m larger than it is.
  - An extent difference in the thousands is called out as almost certainly a
    CRS mismatch, because that is what it almost always is.

31. PROJECT, HISTORY, WORKFLOWS AND COMMAND PALETTE
================================================================================
STATUS: BUILT. Phase 13. core/history.ts, core/workflow.ts, core/project.ts.

31.1 OPERATION HISTORY (R19) (BUILT - core/history.ts)
Import, CRS change, repair, edit, snap, burn-in, reproject, simplify, export -
each recorded, each reversible, with checkpoints and project snapshots.

31.2 WORKFLOW BUILDER (BUILT - core/workflow.ts)
Record a sequence and replay it on new data. Example:
  IMPORT DXF -> detect CRS -> repair topology -> polygonise closed polylines
  -> burn text into polygons -> reproject to WGS 84 -> KML -> KMZ -> report
saved as "CAD Parcel to KMZ".
A workflow step that would trigger a confirmation prompt when run by hand MUST
still prompt when replayed, unless the user has explicitly marked that step
unattended. Automation must not become a way to bypass R18.

31.3 PRESETS (BUILT - core/presets.ts)
Twelve presets for jobs people actually do: CAD -> GIS; cadastral DXF ->
labelled polygons; GIS -> CAD; GIS -> Google Earth; cadastral -> labelled KMZ;
borehole CSV -> styled KMZ; survey CSV -> GIS; survey -> Shapefile package;
DEM -> GeoTIFF; point cloud -> LAS; mine survey -> KMZ; archive -> mirrored
delivery. (LiDAR -> DTM and DEM -> contours wait on the Phase 4/5 raster and
surface work.)

A preset exists because the settings that make a job work are not obvious - the
cadastral one needs polygonisation, burn-in, a CRS and a layout in combination -
and expecting every user to rediscover that is how a capable tool ends up used
as a dumb one.

TWO RULES, both asserted by tests rather than left to review:
  - NO PRESET ENABLES ANYTHING DESTRUCTIVE. None sets replaceSource, none turns
    on a repair that moves geometry. A preset is applied WITHOUT being read, so
    what it must never do matters more than what it does (R18).
  - EVERY PRESET SAYS WHAT IT CHANGES, compared against the settings in force
    rather than against the defaults: the user wants to know what is about to
    change for them. A preset that silently rewrites eight settings is a trap
    the next conversion springs.

A further guard: any preset targeting KML or KMZ must set EPSG:4326. Projected
coordinates written into a KML place the geometry in the wrong part of the
world, and the file still opens - so the failure is silent.

31.4 PROJECT FILE (BUILT - core/project.ts)
Saves source references, imported data, transformations, CRS, styles, edits, QA
results, workflows and export configuration, and reopens without losing editing
state. It MUST NOT contain credentials or tokens (R23).

A project file is the most shareable artefact this tool produces: small, JSON,
and emailed. Everything written into one passes through stripSecretsDeep first
and what was removed is LISTED IN THE FILE, so an omission is visible rather
than mysterious.

Sources are recorded as IDENTITIES, not bytes: name, path, size, format and the
SHA-256 the importer already computed. On reopen, matching is on the hash where
both sides have one, because that is the only test that answers the question
that matters - is this the same data the edits were made against? Name and size
agreeing is not the same claim: a re-export from the same CAD file is very often
the same name and a similar size, and replaying a vertex edit onto it would move
the wrong vertex. Where a hash is absent the state is `unverifiable`, never
`same`.

A DEFECT WORTH RECORDING, found while building this. The credential value
pattern was case-SENSITIVE. It matched a lower-case `bearer ` and missed
`Bearer ` - the capitalisation every HTTP header uses and therefore the only one
anyone ever pastes into an attribute table. R23 looked enforced in review and in
the tests while letting the real case through into KMZ balloons. The detection
now lives in core/secrets.ts, once, shared by every writer, with the `i` flag
and a test asserting all three capitalisations.

31.5 COMMAND PALETTE (BUILT - ui/command-palette.ts)
Ctrl/Cmd+K. Commands are built FRESH on every open, not once at start-up,
because most depend on what is selected: "Convert to Shapefile" is meaningless
with nothing queued, and a palette that offers it and then fails is worse than
one that says why it cannot.

The palette is what makes R24 workable. The main screen must stay minimal and
this tool now holds a great deal - polygonisation, burn-in, defect scanning,
presets, CRS selection, a dozen output formats. On the surface that is the
crowded toolbar the master document forbids; in menus it is undiscoverable. A
searchable palette satisfies both constraints at once.

RANKING IS THE FEATURE. A palette that returns the right command fifth is one
people stop using. Scoring, highest first:
  title prefix > title word start > title substring > keyword > group > fuzzy
Every command carries KEYWORDS, because nobody types "Attach text to polygons" -
they type "burn". Fuzzy matching exists as a last resort and is scored so it can
never outrank a real match.

A DISABLED COMMAND STAYS VISIBLE, ranked last, showing why it cannot run instead
of its description. A palette that silently omits what was searched for looks
broken, and the user retypes the same query expecting a different result.

Configurable shortcuts remain open.
