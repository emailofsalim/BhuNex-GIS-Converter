UNIVERSAL CHROME + MICROSOFT EDGE EXTENSION
POWERFUL COMPUTATION-FIRST ARCHITECTURE SPECIFICATION
============================================================
VERSION 2.0
============================================================

PURPOSE
============================================================

This document is the mandatory BASE ARCHITECTURE SPECIFICATION for building
ONE powerful browser extension that runs on BOTH:

1. Google Chrome
2. Microsoft Edge

The extension must be designed as a single Chromium/WebExtension application,
not as two separately maintained applications.

The same source code, same manifest, same UI, same processing engines,
same algorithms, same storage architecture, and same packaged extension
must work in both Chrome and Edge wherever the standards and APIs permit.

The extension is expected to perform complex mathematical calculations,
complex algorithms, computational geometry, large-data processing,
file processing, scientific calculations, engineering calculations,
GIS/Survey/CAD-related algorithms, and potentially other computationally
intensive operations.

Therefore, this is NOT a simple popup extension architecture.

The system must be designed as a serious computation platform capable of
handling CPU-intensive and memory-intensive workloads without freezing
the browser UI.

============================================================

There must be ONE primary:

manifest.json

Do NOT create:

manifest/chrome/manifest.json
manifest/edge/manifest.json

is demonstrated.

16. MEMORY MANAGEMENT
============================================================

Location:

src/core/managers/memory-manager.ts


The extension must be designed with memory usage in mind.

Potential requirements:

- Avoid unnecessary data duplication
- Release unused buffers
- Reuse typed arrays where appropriate
- Process large data in chunks
- Use transferable objects where appropriate
- Avoid retaining references unnecessarily
- Monitor long-running tasks
- Prevent uncontrolled cache growth


Large datasets must not be loaded into memory repeatedly without reason.

27. NUMERICAL CORRECTNESS
============================================================

For mathematical operations, correctness is more important than merely
producing a plausible answer.

Where appropriate:

- Compare against known reference values.
- Use tolerance-based comparison for floating-point calculations.
- Use exact arithmetic where possible.
- Document numerical assumptions.
- Document approximation methods.
- Report precision/accuracy limitations where relevant.


Never hide numerical instability.


============================================================
28. ERROR HANDLING
============================================================

Distinguish:

1. Invalid input
2. Mathematical domain error
3. Numerical instability
4. Algorithm failure
5. Worker failure
6. Memory/resource failure
7. Browser API failure
8. Permission failure
9. File parsing failure
10. Internal programming error


The system must return useful errors.

Example conceptual result:

SUCCESS
{
  result: ...
  precision: ...
  executionTime: ...
}


FAILURE
{
  errorType: ...
  message: ...
  details: ...
  taskId: ...
}


Never silently return an incorrect result.


============================================================
29. SECURITY REQUIREMENTS
============================================================

The extension must use secure practices.

Mandatory principles:

- Minimum permissions
- Validate all external/page input
- Validate imported files
- Validate worker messages
- Do not execute arbitrary user input as JavaScript
- Do not use unsafe dynamic code execution
- Avoid unnecessary remote code
- Keep sensitive information out of URLs
- Restrict access to extension resources
- Validate data before processing


Mathematical expression parsing must be implemented safely.


============================================================
30. OFFLINE-FIRST COMPUTATION
============================================================

The computational engine should work offline wherever the functionality
does not inherently require an external service.

Core mathematics and algorithms should be locally bundled.

Do not make basic calculations dependent on an internet connection.

Network-dependent functionality must fail gracefully when offline.

============================================================
33. EXECUTION STRATEGY
============================================================

The system should not automatically use the heaviest technology for every
operation.

Choose execution strategy based on workload.

Conceptually:

SMALL / SIMPLE
    -> Main thread when safe

MODERATE
    -> Worker

LARGE
    -> Worker + chunking

PARALLEL
    -> Worker pool

EXTREMELY CPU-INTENSIVE
    -> Worker + WASM where beneficial


The objective is maximum practical performance without unnecessary
complexity.


============================================================
34. LARGE DATA PROCESSING
============================================================

For large files or datasets:

Do NOT assume the complete dataset must always be loaded and duplicated
in memory.

Where practical:

- Stream
- Chunk
- Process incrementally
- Use typed arrays
- Use transferable buffers
- Aggregate results
- Release temporary memory


Algorithms must document if they require the entire dataset in memory.

41. STRICT DEPENDENCY RULES
============================================================

Do not allow uncontrolled dependencies.

Core mathematics should not depend on UI.

Core algorithms should not depend on popup.

Workers should not depend on DOM APIs.

Browser adapters should not contain mathematical logic.

Storage should not contain algorithm logic.

UI should not contain computational engines.


Maintain clean dependency direction.


============================================================
42. NO GIANT FILES
============================================================

Never create files containing the entire application.

Do not create:

- one giant app.ts
- one giant popup.ts
- one giant service-worker.ts
- one giant math.ts
- one giant algorithms.ts
- one giant utils.ts


Break the system into logically independent modules.


============================================================
43. NO UNNECESSARY REWRITES
============================================================

When adding a feature:

1. Inspect the existing architecture.
2. Identify the correct module.
3. Add the feature there.
4. Reuse existing infrastructure.
5. Preserve existing behaviour.
6. Add tests.
7. Only refactor unrelated architecture if technically necessary.


Do not rewrite stable modules simply to add a new feature.
